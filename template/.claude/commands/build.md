Run the Full loop of `.paperclip/HARNESS.md` on: **$ARGUMENTS**

(Requires Paperclip ON. You are the orchestrator — the acting C-level, normally the CTO. You never write the code yourself. `pc` is `.paperclip/bin/pc` — call it by that path if it is not on yours. The numbers below that are the Founder's — slice size, surprise limit, who approves what, what a pause does, the undo policy — are HARNESS §9, **Founder policy**. Many independent units against one contract is `/campaign`, not this; independent slices of a build may fan out as a `/campaign` wave under the same one-writer-per-file rule.)

0. **Triage first** (HARNESS §1). A mini-order goes through `/task` (Direct) — do not run this loop for micro work. Small but uncertain goes to `tech-lead` (Guided). Only Full continues.
1. **Open the build.** `<build>` = `<yyyymmdd>-<slug>`. `pc campaign new "<build>: <title>" --contract .paperclip/orders/<build>.md --goal "True when done: … · Not doing: … · Could break: …"` — the goal card, shown in your kickoff message, not a blocking question. Read `pc estimate` for `plan`, `critique`, `probe`, `build-slice` and `checkpoint`: any time you quote comes from history, or you say there is none.
2. **Plan.** `pc task new "<build> plan" --class plan --role tech-lead --scope .paperclip/orders/<build>.md --campaign <c-id> --contract .paperclip/orders/<build>.md --model <what it runs on>`, then `tech-lead` in PLAN mode with the goal card and the brief `.paperclip/briefs/README.md` lists for it. Relay any upward question to the Founder as a no-brainer question. When the order exists, write its slice sequence into the campaign file's `## Tasks` — one line per slice and its allowed paths.
3. **Attack — every Full build.** `pc task new "<build> critique 1" --class critique --role critic --campaign <c-id> --contract .paperclip/orders/<build>.md` (no scope: the critic writes nothing; the warning is expected). The critic is read-only, so you keep its ledger: `pc task start`, a fresh `critic` on the order, its reply saved verbatim as `.paperclip/orders/<build>.critique-1.md`, `pc task done <id> --note "VERDICT … · N objections"`. Resume `tech-lead` until every objection is fixed in the order or refuted with evidence (answers appended to the critique file); you arbitrate what is left, and you approve any order that touches a seam.
4. **Probes.** One `--class probe --role tech-lead` task per unproven load-bearing assumption (no scope — nothing durable). No slice task exists while one is open.
5. **Where the code is written** (HARNESS §8). The repo's worktree flow if it has one; otherwise ask the Founder where the code is written. Cutting the branch/worktree is the Founder's go — ask once per build, in the same question as the undo policy (local slice commits, or snapshots). Enter the worktree (`EnterWorktree` with its `path`) so every agent works from inside it, prove the ledger and the order are writable from there (HARNESS §8 — and its fallback if they are not), run the order's "Worktree prerequisites", and have `tech-lead` prove each gate command once inside before slice 1. The repo's migration rule applies.
6. **Slice loop — one slice at a time.**
   - Create the next slice's task only now: `pc task new "<build> S<n> — <name>" --class build-slice --role engineer --model <from the order> --scope <its allowed paths>… --gates <gate names> --campaign <c-id> --contract .paperclip/orders/<build>.md`. A refusal means the slice would write what live work owns: resolve it, never `--force` past it.
   - Launch `engineer` (the order's model; a hard slice gets the stronger model through the per-call override) with the slice brief from `.paperclip/briefs/README.md` — blocks only; everything the slice says is already in the order.
   - Then `pc task new "<build> S<n> checkpoint" --class checkpoint --role tech-lead --scope <the slice's allowed paths>… --campaign <c-id> --contract …`, and resume `tech-lead` in CHECKPOINT mode with both task ids, the branch name and the build's undo mode (the grant sentence, or "snapshot to `.paperclip/orders/<build>.snapshots/`"). Act on the verdict.
   - The first slice's evidence is approved as policy says. Resume the same agents across slices (`SendMessage`); start fresh ones only when their context is gone. A slice in flight is never amended. An independent slice (paths disjoint from everything uncommitted — `pc` refuses any overlap with the running checkpoint) may run beside the previous checkpoint: tell both agents what else is in flight.
7. **Surprise rule.** Count the slice task's `surprise:` notes (`pc task show <id>`). At the policy's limit the checkpoint says `RE-PLAN`. What a pause does is policy — by default the first re-plans automatically (a new `plan` task, a `critique` task on the changed part only, continue, tell the Founder afterwards), and the second stops: `pc task block <the waiting task> --on founder`, `pc notify blocked "<the question>"`, mirrored into STATUS §1 with your recommendation.
8. **Close.** A `--class review` task for a fresh reviewer (`/code-review`, or a fresh agent) with the order in hand, filing every finding as `pc finding new --from <review-task> … --title "[plan-gap] …"` or `"[execution-gap] …"` · the real-client pass if the repo's rules require it · the full suite at most twice (here and after the review's fixes), output written to files · every finding fixed (a mini-order claims it: `pc finding claim`, then `pc finding fix`) or closed with a reason · leave the worktree (Founder's go) · a `--class close` task whose done note is the tally (HARNESS §7) · `pc campaign close <c-id>` — it refuses while anything is open, and that refusal is the close gate · `STATUS.md` · then report to the Founder: verdict first, evidence, the tally, what is left, what needs the Founder's go (commit, push, PR).
